# 内存观测

本文整理 Android App 内存观测口径：`malloc`、`mmap`、`smaps`、`dumpsys meminfo`、`memtrack/Graphics` 各自能回答什么，不能回答什么，以及在 FS/Unity 场景中的推荐排查顺序。

核心结论：

- 只 hook `malloc` 和 `mmap` 不能覆盖应用所有内存分配。
- `malloc` 适合看 native heap 对象级分配；`mmap` 适合看 VMA 生命周期和物理驻留归因。
- Java/IL2CPP managed heap、GPU/Graphics/memtrack、Surface/BufferQueue、驱动内部内存都有独立口径。
- `dumpsys meminfo` 是总量对账入口；`smaps` 是进程 VMA 驻留内存入口；memtrack 是 smaps 覆盖不到的设备内存补充。

## 总览

| 观测对象 | 推荐入口 | 能回答 | 不能回答 |
|---|---|---|---|
| Native malloc/new | Perfetto heapprofd、`run_heap_profile.sh`、`heap_analyzer` | 哪些 native 调用栈产生 malloc live bytes | 不覆盖 Java 对象、GPU 资源；采样口径受 interval 和 heapprofd 健康状态影响 |
| mmap/VMA | `run_mmap_phys_profile.sh`、mmap syscall + smaps | 哪些 mmap 调用栈最终占用了 PSS/RSS | 不知道 VMA 内部 allocator 对象；无栈模式不能做调用栈归因 |
| 当前物理驻留 | `/proc/<pid>/smaps`、`smaps_rollup` | VMA 级 PSS/RSS/Private Dirty/Private Clean | 只能看快照，不包含未映射到进程 VMA 的设备内存 |
| Android 汇总 | `adb shell dumpsys meminfo <package>` | Native Heap、mmap、Unknown、Graphics、SQL 等主表和 App Summary | 不是调用栈工具；部分字段来自不同来源，不能直接互相相加 |
| Graphics/memtrack | `dumpsys meminfo` 的 `EGL mtrack`、`GL mtrack`、`Other mtrack`、App Summary `Graphics` | 设备/HAL 愿意归因给该 pid 的图形/GL/其他设备内存 | 没有资源级调用栈；设备和 GPU 驱动依赖强 |
| Unity 资源 | Unity Memory Profiler、Unity Profiler | Texture、Mesh、RenderTexture、AssetBundle 等引擎资源 | 与系统 PSS/memtrack 口径不同，需要和 meminfo 对账 |
| GL/Vulkan 资源 | hook GL/Vulkan API 或引擎封装层 | texture/buffer/image 创建点和大小 | 实现成本高，需要覆盖 API 和生命周期 |

## 为什么 `malloc + mmap` 不等于所有内存

| 内存来源 | `malloc` hook | `mmap` hook | 说明 |
|---|---:|---:|---|
| bionic/scudo `malloc/calloc/realloc/free` | 可见 | allocator 扩容时可见 | malloc 能看对象级；mmap 只能看到 allocator 向系统拿的大块 region |
| C++ `new/delete` | 通常可见 | allocator 扩容时可见 | 前提是最终走 libc malloc |
| 直接匿名 mmap | 不可见 | 可见 | 需要结合 smaps 才知道是否触页、PSS 多少 |
| 文件 mmap、`.so/.apk/.dex/.art` | 不可见 | 可见 | 主要进入 meminfo 的 mmap 行 |
| Java/Kotlin 对象 | 不可见 | 只能看到 ART heap VMA | 对象分配在 ART 内部，需要 Java heap 工具 |
| IL2CPP/Unity managed object | 通常不可见 | 只能看到底层 heap/arena | 需要 Unity/IL2CPP 侧工具或运行时统计 |
| Thread stack | 不可见 | VMA 可见 | 不是分配器分配对象 |
| dmabuf/Surface/GraphicBuffer | 不可见 | 只覆盖映射进进程的部分 | 未映射或驱动内部归因依赖 memtrack/SurfaceFlinger |
| GL/EGL/Vulkan 资源 | 不可见 | 通常不完整 | 系统总量看 memtrack，资源归因看 GL/Vulkan/Unity 层 |

因此，`malloc + mmap` 是 native 侧非常重要的互补组合，但不是“全应用所有内存”的全集。

## 口径关系

| 口径 | 粒度 | 时间属性 | 典型字段 | 使用方式 |
|---|---|---|---|---|
| malloc live | 调用栈/分配对象 | 采集窗口内 live 净值 | `heap_profile_allocation` live bytes | 找 native heap 分配点 |
| mmap PSS | mmap 调用栈/VMA 重叠 | smaps 快照时刻 | `pss_bytes`、`rss_bytes`、`virtual_bytes` | 找 mmap 造成的物理驻留 |
| smaps PSS | VMA | 单个快照 | `Pss`、`Rss`、`Private_Dirty` | 判断当前真实驻留页 |
| meminfo 主表 | Android 分类 | 单个快照 | `Native Heap`、`.so mmap`、`Unknown`、`EGL mtrack` | 总量对账和方向判断 |
| meminfo App Summary | 聚合分类 | 单个快照 | `Java Heap`、`Native Heap`、`Graphics`、`Private Other` | 快速识别主要方向 |
| memtrack | pid + 类型 | 单个快照 | `EGL mtrack`、`GL mtrack`、`Other mtrack` | 观察 smaps 外的设备/GPU 内存 |

注意事项：

- `mmap PSS` 不等于 `meminfo Native Heap PSS`。
- `Native Heap Heap Alloc` 是 allocator 账面分配，不是 PSS。
- `smaps total PSS` 通常小于 `meminfo TOTAL PSS`，差异可能来自 `EGL/GL mtrack` 等非 VMA 口径。
- App Summary 的 `Native Heap` 使用 native private dirty，更偏“进程退出可释放的私有内存”；主表 `Native Heap Pss Total` 是 PSS。

## memtrack/Graphics 观测

`memtrack/Graphics` 先用 `dumpsys meminfo` 做总量观测，再用 Unity/GL/Vulkan/SurfaceFlinger 做资源级归因。

```bash
adb shell dumpsys meminfo <package>
```

重点看主表：

```text
Gfx dev
EGL mtrack
GL mtrack
Other mtrack
```

以及 App Summary：

```text
Graphics
```

解释：

| 字段 | 来源 | 是否来自 smaps | 解读 |
|---|---|---:|---|
| `Gfx dev` | smaps 中已映射进进程的 GPU 设备 VMA，例如 `/dev/kgsl-3d0` | 是 | 只覆盖进程地址空间可见的设备 VMA |
| `EGL mtrack` | memtrack HAL graphics 类型 | 否 | 常见于 GraphicBuffer/Surface/EGL 相关归因 |
| `GL mtrack` | memtrack HAL GL 类型 | 否 | 常见于 texture、buffer、driver GL 资源归因 |
| `Other mtrack` | memtrack HAL other 类型 | 否 | 设备相关其它类型，主表可见，但通常不计入 App Summary `Graphics` |
| App Summary `Graphics` | `Gfx dev + EGL mtrack + GL mtrack` 的 private 口径 | 混合 | 快速判断图形内存方向 |

限制：

- memtrack 依赖设备 HAL 和 GPU 驱动，跨设备可比性弱。
- memtrack 给的是 pid/type 总量，不给资源创建调用栈。
- 某些 Surface、dmabuf、驱动内部内存可能无法稳定归到目标 pid。
- 对 Unity 应用，memtrack 增长只能说明图形侧总量变化，不能直接说明是哪张 Texture 或哪个 RenderTexture。

## 推荐排查顺序

### 1. 先看总量方向

```bash
adb shell dumpsys meminfo <package>
```

优先看 App Summary：

| App Summary 项 | 下一步 |
|---|---|
| `Native Heap` 高 | 跑 `run_heap_profile.sh`，用 heapprofd + pprof/分类看 native malloc 调用栈 |
| `Graphics` 高 | 看 `EGL mtrack/GL mtrack/Gfx dev`，再结合 Unity Memory Profiler、SurfaceFlinger、dmabuf/GL/Vulkan |
| `Private Other` 高 | 看主表 `Unknown`、`Other mmap`，再抓 smaps 和 mmap 归因 |
| `Java Heap` 高 | 用 Android Java heap/ART 工具，不要用 malloc/mmap 代替 |
| `Code` 高 | 看 `.so/.apk/.dex/.oat/.art mmap`，结合包体、加载库、dex/oat/art image |

### 2. Native Heap 高

```bash
./run_heap_profile.sh
```

使用要点：

- AI 验证时不要传 duration 参数。
- App PID 就绪后执行 `config.sh` 配置的测试模块；默认 GM 模块复用 FS 登录与表加载步骤，RPC 成功后自行等待 120 秒。其他模块在自身协程的准确阶段调用异步等待，协程返回后收尾。
- 对账看 heapprofd live bytes 与 `dumpsys meminfo` Native Heap Alloc / Native Heap PSS 的关系。

### 3. mmap/Unknown/Other mmap 高

```bash
./run_mmap_phys_profile.sh
```

使用要点：

- 主功能采 mmap 调用栈，适合回答“哪个 mmap 调用栈最终占了 PSS/RSS”。
- 无栈验证只检查 mmap syscall events + smaps 健康状态，不启用 heapprofd malloc。
- `mmap_health_report.md` 中 smaps 分类用于和 meminfo 对账；不要把 `mmap PSS` 当作 `Native Heap PSS`。

### 4. Graphics 高

先抓：

```bash
adb shell dumpsys meminfo <package>
adb shell dumpsys SurfaceFlinger
```

如果需要资源级归因：

| 场景 | 建议 |
|---|---|
| Unity Texture/Mesh/RenderTexture | Unity Memory Profiler / Unity Profiler |
| OpenGL ES | hook `glTexImage*`、`glBufferData`、`glRenderbufferStorage`、`glDelete*` |
| Vulkan | hook `vkAllocateMemory`、`vkCreateImage`、`vkCreateBuffer`、`vkDestroy*` |
| Surface/BufferQueue | SurfaceFlinger、Window/Layer/BufferQueue dumpsys |
| dmabuf/ION | 设备支持时看 dmabuf/ion/debugfs 统计，注意权限限制 |

## 对账原则

| 对账对象 | 是否应该相等 | 原因 |
|---|---:|---|
| `malloc live bytes` vs `Native Heap Heap Alloc` | 接近但不要求完全相等 | heapprofd 采样、启动前分配、allocator 统计和采集窗口会造成差异 |
| `Native Heap PSS` vs `Native Heap Heap Alloc` | 不要求相等 | 一个是驻留物理页，一个是 allocator 账面分配 |
| `mmap PSS` vs `meminfo Native Heap PSS` | 不应要求相等 | mmap PSS 覆盖所有 live mmap 与 smaps 重叠，不是 Native Heap 子集 |
| `smaps total PSS` vs `meminfo TOTAL PSS` | 不要求相等 | meminfo TOTAL 可能包含 memtrack HAL 上报的 EGL/GL/Other mtrack |
| `Graphics` vs `EGL + GL mtrack` | 通常接近 | App Summary `Graphics` 主要由 `Gfx dev + EGL mtrack + GL mtrack` 聚合 |
| Unity Memory Profiler texture size vs `GL mtrack` | 只能趋势对比 | 引擎资源账面大小、压缩格式、mipmap、驱动分配和对齐都会造成差异 |

## 最小实战判断

看到一次 `dumpsys meminfo` 后，按这个顺序判断：

1. `TOTAL PSS` 是否真的高。
2. App Summary 里最大的是 `Native Heap`、`Graphics`、`Private Other`、`Java Heap` 还是 `Code`。
3. 如果是 `Native Heap`，用 heapprofd/malloc profile。
4. 如果是 `Graphics`，用 memtrack 总量 + Unity/GL/Vulkan/SurfaceFlinger 资源归因。
5. 如果是 `Private Other` 或主表 `Unknown/Other mmap` 高，用 smaps + mmap 归因。
6. 如果 `smaps total PSS` 和 `meminfo TOTAL PSS` 差很多，先看 `EGL mtrack/GL mtrack/Other mtrack`，不要假设 mmap 或 malloc 采集丢了。
