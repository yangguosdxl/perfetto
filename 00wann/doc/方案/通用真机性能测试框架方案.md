# 通用真机性能测试框架方案

## 背景

`run_heap_profile.sh` 和 `run_mmap_phys_profile.sh` 已共享部分配置、宿主机工具探测和
测试脚本执行器，但完整真机测试流程仍分别实现在 `run_heap_profile.py` 与
`collect_mmap_phys_data.py` 中。当前重复或耦合的内容主要包括：

- 读取目标 App、设备、工具和测试脚本配置；
- 检查设备、停止/启动 App、等待 PID、采集 logcat、判断进程存活；
- 等待登录和表加载检查点、运行测试脚本、处理超时和中断；
- 创建输出目录、记录关键配置和阶段结果；
- 采集结束后生成专业报告，但缺少统一的本轮运行清单和总报告。

malloc 与 mmap 的采集顺序和验证口径并不相同，不能为了复用而合并成大量条件分支：

- malloc：heapprofd 先启动并进入 active，再启动 App；采集结束时先请求 profiler
  shutdown，并在特定时点抓 meminfo。
- mmap：生命周期 Perfetto 必须先于 App；PID 出现后再启动调用栈会话和 smaps；
  无栈验证还有独立的固定 45 秒语义。

因此框架抽取公共生命周期，malloc/mmap 保留为显式功能插件。

`config.sh` 当前先无条件设置正式包名，再使用 `${MMAP_PHYS_APP:-...}`，是为了方便
当前真机测试的临时强制覆盖。它不是本次要修复的配置缺陷；迁移期间保持原样兼容，
通用配置加载器只负责把最终环境值归一化。

## 设计结论

```text
                         run_device_test.py
                                 |
                  DeviceTestEngine（阶段编排）
                   /             |              \
                  /              |               \
       PlatformAdapter       FeaturePlugin       FlowSpec
       设备与目标进程          采集/分析/报告       测试场景
            |                      |                 |
      AndroidAdapter          malloc / mmap      登录/表/GM
      后续 iOSAdapter         显式插件注册表       完成条件
      后续 WindowsAdapter
                  \              |               /
                   \             |              /
                    RunContext + Result + Artifact
                                 |
             run_manifest.json / run_summary.txt / report.md
```

采用三个小而明确的扩展点：

1. `PlatformAdapter`：设备连接、App/进程、日志、文件和端口转发。
2. `FeaturePlugin`：malloc、mmap 等采集功能及其专业分析和报告。
3. `FlowSpec`：登录检查点、测试操作、稳定等待和场景完成条件。

不引入动态包发现、事件总线或第三方插件管理器。插件通过代码内显式注册表按名字加载，
便于查错和测试。

```python
@dataclass(frozen=True)
```

每轮在操作真机前打印归一化关键配置，并写入 `run_config.json`。敏感值如密码只记录
是否设置，不写明文。

统一命令：

```bash

./run_device_test.sh malloc --interval-bytes 1024 --shmem-size-bytes 8388608
./run_device_test.sh mmap
./run_device_test.sh mmap --mode no-stack-validation
```

Python 核心入口（功能为位置参数）：

```bash
python run_device_test.py \
  --platform android \
  --flow fs_login_battle \
  malloc
```

兼容入口：

```text
run_heap_profile.sh [interval_bytes] [shmem_size]
  -> run_device_test.sh malloc --interval-bytes ... --shmem-size-bytes ...

run_mmap_phys_profile.sh [...旧参数]
  -> run_device_test.sh mmap [...原参数]
```

入口只做工作目录、配置文件和 Python 探测；ANR 对话框处理等 Android 专有操作移入
`AndroidAdapter` 的 run scope，不再由通用 Shell 入口调用。

## 3. 平台适配层

### 协议

```python
class PlatformAdapter(Protocol):
  def validate_connection(self) -> OperationResult: ...
  def describe_target(self) -> DeviceInfo: ...
  def stop_app(self, target: TargetSpec) -> OperationResult: ...
  def start_app(self, target: TargetSpec) -> OperationResult: ...
  def wait_process(self, target: TargetSpec, timeout_s: float | None) -> ProcessResult: ...
  def is_process_alive(self, process: ProcessHandle) -> bool: ...
  def start_log_capture(self, output: Path) -> ResourceResult: ...
  def push_file(self, source: Path, destination: str) -> OperationResult: ...
  def pull_file(self, source: str, destination: Path) -> OperationResult: ...
  def forward_port(self, local: int, remote: int) -> ResourceResult: ...
  def capture_memory_snapshot(self, process: ProcessHandle, output: Path) -> OperationResult: ...
  def close(self) -> OperationResult: ...
```

资源型操作返回可关闭句柄，由框架统一登记并按逆序清理。运行失败返回结果对象，不直接
让平台实现决定整轮是否失败；框架根据阶段要求统一判断。

### Android 实现

`AndroidAdapter` 统一封装：

- `adb -s <serial>` 和连接校验，只允许配置的设备；
- `am force-stop`、`am start`、`pidof` 和原 PID 存活检查；
- logcat 清理、采集和按 PID 日志输入；
- `adb push/pull`、Perfetto 设备文件和 `dumpsys meminfo`；
- ADB 端口转发；
- 采集期间隐藏系统错误对话框并在 `close()` 恢复。

当前 `common_tools.sh`、`run_heap_profile.py` 和 `collect_mmap_phys_data.py` 中散落的
Android 操作逐步迁入该适配器。

### iOS 和 Windows 扩展

v1 不伪造不可验证的 iOS/Windows 实现，只提供稳定协议和注册点：

```text
android -> adb / logcat / perfetto / port forward
ios     -> 后续 devicectl 或 ios-deploy / syslog / iproxy
windows -> 后续本机或远端进程管理 / ETW / 直接 TCP
```

功能插件声明所需能力，例如 `process_memory_snapshot`、`perfetto`、`port_forward`。
框架在开始前检查平台能力并明确失败，不在运行中通过平台名散布 `if android`。

## 4. 通用测试脚本系统

### 声明式流程

常见场景使用配置式 `FlowSpec`：

```python
FLOW = FlowSpec(
    name="fs_login_battle",
    checkpoints=[
        AppLogCheckpoint("登录场景完成"),
        AppLogCheckpoint("RegistForGameStart.LoadOtherTable.End", timeout_s=180),
    ],
    actions=[
        RpcAction(
            method="DoRecordCheat",
            params=["CheatFunc_BatchCheatOption.战斗录像:@40011@@|"],
        ),
    ],
    collection_wait_seconds=120,
)
```

`RpcAction` 继续使用当前 `ProfileActionSession` 的默认约定：

- 默认要求 `result=True`；
- 默认写 `gm_rpc.txt`；
- 公共接口运行失败返回 `success=False`；
- 动作声明的 `fail_run_on_error=True` 决定是否让本轮失败。

登录和表加载检查点从两个采集器中移出，成为流程的一部分。采集插件只关心何时开始
和停止数据源，不再知道“登录场景完成”或具体 GM。

### 复杂流程

声明式动作不足时允许流程模块实现：

```python
async def run(session: DeviceTestSession) -> FlowResult:
  ...
```

`DeviceTestSession` 在现有 `ProfileActionSession` 基础上改为持有
`PlatformAdapter`，提供平台无关的日志、进程、端口转发和动作结果。现有
`get_collection_wait_seconds()` / `run_profile_action()` 模块通过兼容适配器继续运行，
待现有脚本迁移后再删除兼容层。

### 流程与采集的竞速

```text
FeaturePlugin.before_launch()
  -> PlatformAdapter.start_app()
  -> FeaturePlugin.after_process_started()
  -> Flow checkpoints + actions
  -> 流程完成 / 等待时间到 / 人工中断 / 原 PID 死亡
  -> 取消流程并等待 Session 清理
  -> FeaturePlugin.stop()
  -> collect -> analyze -> validate -> report
```

无栈 mmap 验证属于 `mmap` 插件的 `no-stack-validation` 模式：保持 Perfetto 先于 App、
重启 App、固定 45 秒、不执行登录后流程脚本，不被通用 Flow 改变。

## 5. 功能插件系统

### 是否插件化

结论：做成小型显式插件系统，但 v1 每轮只启用一个主采集插件。

原因：

- malloc/mmap 共享生命周期阶段，但启动、停止、采集物和验证完全不同；
- 后续增加 GPU、启动耗时或网络采集时，不应继续膨胀统一控制器；
- 当前规范明确某些验证不能混入 heapprofd，任意多插件组合会改变负载和统计口径。

注册方式：

```python
FEATURES = {
    "malloc": MallocFeature,
    "mmap": MmapFeature,
}
```

不扫描目录、不使用 Python entry points、不自动加载未知插件。

### 生命周期协议

```python
class FeaturePlugin(Protocol):
  name: str
  required_capabilities: frozenset[str]

  def validate(self, context: RunContext) -> OperationResult: ...
  def prepare(self, context: RunContext) -> OperationResult: ...
  def before_launch(self, context: RunContext) -> OperationResult: ...
  def after_process_started(self, context: RunContext) -> OperationResult: ...
  def stop(self, context: RunContext) -> OperationResult: ...
  def collect(self, context: RunContext) -> OperationResult: ...
  def analyze(self, context: RunContext) -> OperationResult: ...
  def validate_output(self, context: RunContext) -> OperationResult: ...
  def artifacts(self, context: RunContext) -> list[Artifact]: ...
  def close(self, context: RunContext) -> OperationResult: ...
```

所有已获得的可关闭资源登记到 `RunContext.resources`，框架 `finally` 按逆序清理。
插件方法的运行失败统一转成 `OperationResult` 和阶段记录；明显的插件编程错误由框架
捕获后标记 `framework_error`，仍执行清理。

### malloc 插件

首轮迁移不重写 Perfetto `heap_profile.py`，只把现有代码按职责移动：

```text
prepare              -> 工具和符号路径、FS 配置文件准备
before_launch        -> 启动 heap_profile.py，等待 Profiling active
after_process_started-> 无额外采集器；记录 PID
stop                 -> SIGINT，等待 Waiting for profiler shutdown
collect              -> trace/heap dump/meminfo 落盘
analyze              -> 现有 heap 分析入口
validate_output      -> heap dump/health/meminfo 口径报告
```

### mmap 插件

```text
prepare              -> root traced_perf 状态和 Perfetto 配置
before_launch        -> 启动生命周期 ftrace 会话
after_process_started-> 启动 perf 调用栈会话和 smaps 线程
stop                 -> 停止 smaps、调用栈和生命周期会话，恢复 traced_perf
collect              -> pull trace、meminfo、smaps
analyze              -> 符号化和 mmap_phys_analyzer.py
validate_output      -> syscall/smaps/buffer/callsite 健康报告
```

## 6. 通用运行引擎

v1 采用兼容后端方式落地，当前实际阶段为：

```text
connect -> platform_scope -> feature_validate -> feature_run
        -> feature_close -> platform_close -> report
```

`feature_run` 内继续运行已经验证过的 `run_heap_profile.py` 或
`collect_mmap_phys_data.py` 完整专业时序。下面的细粒度状态机是后续逐步迁移专业后端时的
目标，不代表 v1 已把 App/PID/logcat/Perfetto 的所有阶段拆入公共引擎。

框架采用固定状态机，而不是让插件自行调用下一阶段：

```text
CONFIGURED
  -> CONNECTED
  -> PREPARED
  -> COLLECTOR_READY
  -> APP_STARTED
  -> FLOW_RUNNING
  -> STOPPING
  -> COLLECTED
  -> ANALYZED
  -> VALIDATED
  -> REPORTED
  -> CLEANED
```

每个阶段记录：

```text
name / status / started_at / ended_at / duration_ms / error / plugin
```

失败策略：

- 连接、prepare、采集器启动、App 启动失败：跳过流程，直接清理并报告失败。
- 流程失败：停止采集，尽量拉回已有数据并继续分析，最终失败。
- collect 失败：继续登记已有产物，能分析的继续分析。
- analyze/validate 失败：保留原始采集数据并报告具体阶段。
- 人工中断：先取消 Flow，再让插件正常 stop/collect，最后清理平台资源。
- 任意失败都不能跳过 `FeaturePlugin.close()` 和 `PlatformAdapter.close()`。

## 7. 报告输出

框架只统一运行级报告，不重写 malloc/mmap 的专业报告。

每轮输出至少包含：

```text
run_config.json       # 归一化配置快照
run_manifest.json     # 平台、设备、功能、流程、阶段、结果和产物索引
run_summary.txt       # 结构化单行日志，兼容现有检查
report.md             # 人工阅读总报告，链接专业报告
profile_action.log    # 流程与动作日志
```

`Artifact` 统一登记：

```python
@dataclass(frozen=True)
class Artifact:
  name: str
  path: Path
  kind: str
  producer: str
  required: bool
  description: str
```

插件专业产物保持现名：

```text
malloc:
  raw-trace / symbolized-trace / heap_dump.*
  dumpsys_meminfo.txt
  heap_meminfo_validation.txt

mmap:
  mmap_trace.perfetto-trace / mmap_callstack_trace.perfetto-trace
  symbolized-trace / smaps/
  mmap_phys_attribution.json / *.pprof.pb.gz
  memory_validation.json
  mmap_health_report.md / mmap_health_report.json
```

`report.md` 展示总状态、阶段耗时、失败阶段、关键配置和专业报告链接。总报告不把
malloc live、Native Heap Alloc、mmap PSS 等不同口径强行合并成一个数值。

输出路径首轮保持兼容：

```text
malloc -> PerfData/mem/<时间戳>/
mmap   -> PerfData/mmap_phys/<时间戳>/
```

## 8. 分阶段迁移

### 阶段 1：公共模型、配置和报告骨架

- 新增 `models.py`、`config.py`、`reporting.py` 和单元测试。
- 生成统一配置快照、manifest 和总报告。
- 两个旧控制器暂不移动，仅把已有结果登记到公共报告。
- 保持所有旧命令和产物路径。

### 阶段 2：Android 平台适配器

- 迁移 ADB 选择、设备校验、App/PID、logcat、push/pull、meminfo、端口转发和
  错误对话框 scope。
- 两个控制器改为使用 `AndroidAdapter`。
- 使用假 ADB 集成测试验证所有命令仍限定配置设备。

### 阶段 3：通用 Flow

- 将登录、表加载和 GM 声明为 `fs_login_battle`。
- 将现有 `ProfileActionSession` 接到 `DeviceTestSession`。
- 保留旧 `PERF_PROFILE_ACTION_SCRIPT` 兼容适配器。
- Native heap 与 mmap 主功能共用同一 Flow；无栈 mmap 明确禁用 Flow。

### 阶段 4：功能插件

- 先迁移 malloc，保持 `heap_profile.py` 子进程和现有验证逻辑。
- 再迁移 mmap，保持双 Perfetto 会话、root traced_perf 和 smaps 顺序。
- 每迁移一个插件，先用现有 Shell 集成测试证明行为等价，再删除原控制器中的重复代码。

### 阶段 5：统一入口和兼容包装

- 启用 `run_device_test.sh/python`。
- 将两个旧 Shell 入口缩减为参数翻译包装。
- 更新 README、malloc、mmap 和新增框架文档。

### 阶段 6：平台扩展

- 有真实 iOS/Windows 测试环境和明确采集功能后再实现适配器。
- 先验证连接、App 生命周期、日志和端口能力，再评估对应采集插件是否可复用。
- 不通过模拟 Android 命令来声称平台支持。

## 9. 验证策略

每阶段必须通过：

- 配置优先级、旧变量映射和配置快照单元测试；
- 平台适配器命令、设备限定、资源逆序清理和失败结果测试；
- Flow 检查点、动作失败策略、超时、取消、原 PID 死亡测试；
- Feature 生命周期顺序和失败后仍 collect/close 测试；
- manifest、Artifact 和 Markdown 链接测试；
- 现有 `test_run_heap_profile.sh`；
- 现有 `test_run_mmap_phys_profile.sh`；
- 全量 Python 单元测试。

涉及 mmap 采集调用栈实现的迁移，用主功能自动测试和后续真实场景验证，不用无栈验证
代替。只修改无栈相关代码时，继续按项目规范执行 Perfetto 先于 App、重启 App、45 秒
的真机无栈验证。

## 10. 预计收益

```text
新增平台：实现 PlatformAdapter，不复制 malloc/mmap 流程
```
